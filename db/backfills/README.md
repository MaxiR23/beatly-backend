# db/backfills

SQL data backfills, generated by a script under `scripts/`. Files here
have no number. Unlike `db/migrations/`, which is applied history and
never edited, a file in this directory is regenerated on purpose: if its
generator or its `N` changes, the `.sql` file is regenerated and
versioned together with that change, and a test
(`test/scripts/test_generate_playlist_tracks_order_key_backfill.py`)
fails if the versioned file does not match what the generator produces.
Files here are also re-applied to Supabase by hand, as many times as
their entry below says.

None of this is applied as a migration and none of it is part of the new
database build path: on a fresh database, over an empty `playlist_tracks`
table, running a file here does nothing. A file here is never run from an
agent session.

## Files

### `playlist_tracks_order_key.sql` (#133)

What it does: a lookup of `(position, order_key)` for `position` 1..N
(`N = 10000`), and an `UPDATE ... FROM` that sets `order_key` for every
row whose `position` matches a row in the lookup, filtered with `AND
pt.order_key IS DISTINCT FROM k.order_key` so a row that already carries
the right key is not rewritten. Needs
`db/migrations/027_add_playlist_tracks_order_key.sql` applied first — the
column does not exist before that. Because
`generate_n_keys_between(None, None, n)` is stable by prefix (the i-th
key does not depend on `n`), the key for a given `position` never changes
between runs, and the result is equivalent to overwriting every key with
the one matching its current `position`.

How it is regenerated:

    venv/bin/python scripts/generate_playlist_tracks_order_key_backfill.py

Run from the repo root. Not edited by hand — the header of the file says
so too. `test/scripts/test_generate_playlist_tracks_order_key_backfill.py`
fails if the versioned file stops matching what the script produces.

When it is run: it can be re-run safely. A row inserted after a run keeps
`order_key IS NULL` until the next run — nothing here or in the
application fills it. A reorder inside a playlist between runs leaves
that playlist's keys out of sync with its `position` values until the
next run. The last run has to happen right before the change that starts
reading `order_key` (a later issue).

Triggers and locks: the file disables `trg_bump_playlist_on_track_change`
right after `BEGIN` and re-enables it right before `COMMIT`, both inside
the same transaction, so `public.playlists.updated_at` does not move
because of this backfill — that trigger runs `update playlists set
updated_at = now()` per touched row on every `INSERT`, `DELETE` or
`UPDATE` on `playlist_tracks`, with no column filter. The `ALTER TABLE
... DISABLE/ENABLE TRIGGER` statements take a table-level lock that
blocks concurrent writes to `playlist_tracks` until `COMMIT` (per
`ALTER TABLE`'s documentation; not verified against the instance) —
since this backfill never touches `playlists`, there is no reverse lock
order against the write protocol of `013`, so this cannot deadlock with
`add_playlist_track`, `remove_playlist_track` or `move_playlist_track`.
Disabling and enabling a trigger needs to be the table owner
(`postgres`). `trg_playlist_tracks_reorder` is never mentioned in the
file: the `UPDATE`'s `SET` only writes `order_key`, and the current body
of `playlist_tracks_reorder()` (`022`) returns `NEW` immediately when
`playlist_id` and `position` are unchanged (`022` lines 295-297), so that
trigger does nothing in response to this `UPDATE`. The `DO $$ ... $$;`
block right before `COMMIT` aborts the whole transaction — undoing the
`DISABLE`, the `UPDATE` and the `ENABLE` together, because `ALTER TABLE`
catalog changes are transactional — if, after the `UPDATE`, any row is
left with `order_key IS NULL`, any `(playlist_id, order_key)` pair
repeats, or the order by `order_key COLLATE "C"` does not match the order
by `position` for any playlist. A row with `position > N` falls under one
case or the other depending on whether it already carries a key. If it
never had one — for example, inserted into the window after the last run
— it falls under the first case: it never matches a row in the lookup and
stays `NULL`. If it carries a key from an earlier run — for example,
pushed past `N` by a reorder since then — it does not match the lookup
either, but it keeps that stale key instead of turning `NULL`; the `DO`
block then aborts under the second case once the lookup assigns that same
key to whichever row now sits at the position the stale key was generated
for. Either way, the fix is to raise `N` in the script, regenerate, and
run again.

#### Before every run

(1) Triggers on `playlist_tracks`:

```
set search_path to '';
select t.tgname, t.tgenabled, pg_catalog.pg_get_triggerdef(t.oid) as def
from pg_catalog.pg_trigger t
where t.tgrelid = 'public.playlist_tracks'::regclass
  and not t.tgisinternal
order by t.tgname;
```

should return exactly 2 rows. If a row comes back without `public.`
qualifying the function in `def`, the `set` did not take in that
session — run the two statements together; that alone is not drift, same
note as `025`/`026`. `trg_bump_playlist_on_track_change`'s `def` must
match `017` line 2110 without the trailing `;`, and its `tgenabled` must
be `O`. **If it is not `O`, do not run this file** — the `ENABLE TRIGGER`
inside it would flip the live state instead of restoring it.
`trg_playlist_tracks_reorder`'s `def` must match `017` line 2131 without
the trailing `;`; its `tgenabled` is noted, not asserted — as of
2026-09-23 the live value is `D`, same as `017`'s dump (line 2133), and
the note calling it ACTIVE in `db/migrations/README.md` is known to be
wrong (out of scope for #133) — and has to read the same after the run.

(2) Body of `playlist_tracks_reorder()`, unaffected by this file but
worth confirming nothing else changed it: the md5 query from the `022`
entry of `db/migrations/README.md`, pointed only at
`playlist_tracks_reorder`, must return `43cbfc771352861b14e34d141636f2d3`
— referenced here, not repeated.

(3) and (4): the range and density queries from the `027` entry of
`db/migrations/README.md`. Re-run them every time, not only once, because
`position` values change between runs. (3) gates the run; (4) is
informational only, same as in the `027` entry:

```
select min(position) as min_pos, max(position) as max_pos
from public.playlist_tracks;
```

`min_pos >= 1` and `max_pos <= 10000`. If `max_pos > 10000`, this file
does not run — see the `027` entry for how to raise `N`.

```
select count(*)
from (
  select playlist_id
  from public.playlist_tracks
  group by playlist_id
  having min(position) <> 1 or max(position) <> count(*)
) t;
```

Informational, does not gate the run: `remove_playlist_track` deletes
without renumbering and `trg_playlist_tracks_reorder` is disabled live,
so a non-zero result (some playlist has a gap, or does not start at 1)
is expected and does not affect the backfill — the key generated for
position `p` is increasing in `p` regardless of gaps, and the `DO` block
below compares orders, not position values.

#### After running

Criterion 3 of #133:

```
select count(*) filter (where order_key is null) as null_keys, count(*) as total
from public.playlist_tracks;
```

`null_keys = 0` if checked right after the run. A `NULL` row whose
`added_at` is after the commit is a row inserted in the window after the
run, not a failure of the backfill.

Criterion 4 of #133:

```
select count(*) as mismatches
from (
  select
    row_number() over (partition by playlist_id order by position) as by_position,
    row_number() over (partition by playlist_id order by order_key collate "C") as by_key
  from public.playlist_tracks
) t
where by_position <> by_key;
```

`0`. And, so the query above is deterministic:

```
select count(*)
from (
  select 1
  from public.playlist_tracks
  group by playlist_id, order_key
  having count(*) > 1
) t;
```

`0` — no repeated key inside a playlist.

Re-run query (1) from "Before every run": `trg_bump_playlist_on_track_change`
must still be `O`, and `trg_playlist_tracks_reorder` must have the same
`tgenabled` it had before the run.

A punctual sample for manual QA, on a playlist with a few dozen tracks
and on one with a single track:

```
select position, order_key
from public.playlist_tracks
where playlist_id = '<id>'
order by order_key collate "C";
```

#### If the transaction aborted

The rollback undoes the `DISABLE`, but it is still worth confirming the
trigger came back enabled — this also covers a partial run, for example
only some statements executed in a SQL editor:

```
select tgname, tgenabled
from pg_catalog.pg_trigger
where tgrelid = 'public.playlist_tracks'::regclass
  and tgname = 'trg_bump_playlist_on_track_change';
```

should return 1 row with `tgenabled = O`. If it returns `D`:

```
ALTER TABLE public.playlist_tracks ENABLE TRIGGER trg_bump_playlist_on_track_change;
```

and re-run the check above. `O` is enabled, `D` is disabled.
